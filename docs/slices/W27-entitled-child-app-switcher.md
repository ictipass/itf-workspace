# W27 - Entitlement-aware child-app switcher

Workspace implementation commit: `bc03856`  
ITF Flow implementation commit: `4747f67`

## Outcome

ITF Flow now contains a Workspace-style application switcher in every staff UI variant. The list is generated by
Workspace from the current user's live central session, active app entitlements and active matching role policies.
Workspace remains the authority and complete registry; Flow never receives disabled or unauthorized app entries.

## Security and maintainability boundaries

- Flow's browser calls only its same-origin `/api/workspace/apps` route. That route requires an active Flow session
  originally created through Workspace and forwards the immutable Workspace user and session identifiers server-side.
- Workspace's versioned `/api/integrations/workspace/v1/app-navigation` route requires a dedicated per-environment
  bearer credential, binds the request to the configured Flow slug and revalidates the database-backed Workspace
  session before reading entitlements.
- Only active apps, active access records and active role policies matching the granted role are returned. The current
  source app is excluded.
- Every returned URL points to Workspace's existing `/dashboard/apps/{id}/launch` route. The target launch therefore
  performs its normal current-session, entitlement and MFA checks; child apps do not authenticate one another.
- Flow validates the version, correlation UUID, curated icon key, exact Workspace origin and exact launch-path shape.
  Responses use private `no-store` caching and bounded server-to-server timeouts.
- The credential is separate from launch signing, directory synchronization and session-event delivery. It must be
  unique in each environment and stored as a deployment secret.

## Performance and scalability

The switcher loads lazily only when opened and refreshes on each opening, avoiding a Workspace dependency on every
Flow page render while limiting stale entitlement display. The response is capped at 500 apps and contains only the
small navigation manifest. The current Flow-specific endpoint is intentionally bounded; W17 will generalize connector
credentials and app identities before multiple child apps implement the contract.

## Visible UI effect

- A nine-dot application button appears in the Classic, Modern, Soft UI and Glass staff headers.
- The panel shows entitled applications and a link back to the complete Workspace catalogue.
- A normal app click replaces the current tab; browser Ctrl/Cmd-click and context-menu actions still open a new tab.
- When only ITF Flow is assigned, the current app is excluded and the panel explains that no other applications are
  assigned.
- The Glass header now switches its long navigation into a compact menu when it would collide with search,
  notifications, profile or logout controls, including viewports at or below 1280 pixels.

## Configuration and deployment

Generate one new 32-byte random value per environment and configure the exact same value under these differently named
variables:

- Workspace: `ITF_FLOW_APP_NAVIGATION_SECRET`;
- ITF Flow: `WORKSPACE_APP_NAVIGATION_SECRET`.

Flow may set `WORKSPACE_APP_NAVIGATION_TIMEOUT_MS=3000`; the accepted range is 500-10000 ms. Its
`NEXT_PUBLIC_WORKSPACE_URL` and `WORKSPACE_APP_SLUG` must continue to identify the same Workspace environment and
`itf-flow` registry entry. Deploy Workspace before Flow because Flow consumes the new endpoint. No database migration
or seed is required.

## Rollback

Rollback both application commits together and remove the two navigation variables after the older deployments are
active. There is no data rollback. Removing only one credential while the feature remains deployed causes the switcher
to fail closed with its temporary-unavailable state; it does not expose registry data or bypass target launch checks.
